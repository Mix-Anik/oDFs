# func_0x2575 — Promode flag writer

**Source file:** `D:\Other\Reverse Engineering\q3vm\qagame.dis`  
**Function address:** `0x00002575`  
**Called from:** `0x1a866` (Pmove outer, section 4 — see [../G_ACTIVE/Pmove_outer.md](../G_ACTIVE/Pmove_outer.md#4-promode-flag-update-0x1a8ad0x1a8af)), at `0x1a8ad`, after cmd-input clamping and before commandTime clamping  
**Args:** 1 arg — confirmed **`client` pointer** (`gclient_t*`), not `pmove_t*`. Caller loads `local104 = ent->client` and passes it directly (`arg -1 0x8` from `local 1 0x104`, see qagame.dis:183633-183639). Since `playerState_t ps` is the first member of `gclient_t`, `client` and `&client->ps` are numerically identical addresses — so `arg0 + 0xc` reaching `pm_flags` (ps+0xc, confirmed in [../README.md](../README.md)) is consistent with this being a client pointer, not a `pmove_t*` (pm+0xc falls inside `cmd`, not `pm_flags`).

---

## Purpose

Sets or clears `pm_flags` bit `0x8000` based on whether `df_promode` is enabled.
This is called once per `PmoveSingle` invocation, keeping `0x8000` current every frame.

---

## Logic

```
global_0x1317c4 = df_promode cvar value (cached at game init)

if (global_0x1317c4 != 0):
    pm->ps->pm_flags |= 0x8000     // promode on
else:
    pm->ps->pm_flags &= ~0x8000    // promode off
```

## Relation to df_promode global

`0x1317c4` is written once during game initialization (around address `0x1b70`) by
reading the `"df_promode"` cvar via trap call. It is never updated mid-game.
This means changing `df_promode` in the console requires a map restart to take effect
in the original Defrag build.

---

## Impact on PM_CheckJump

See [[PM_CheckJump]]. The `pm_flags & 0x8000` checks in PM_CheckJump are simply
checking "is promode enabled?" — not a dynamic per-jump window or state flag.
