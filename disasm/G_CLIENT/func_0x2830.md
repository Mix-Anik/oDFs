# func_0x2830 — per-client stale-entity sweep over `g_entities[64..1023]`

**Address:** `0x2830`
**Stack frame:** `enter 0x34`
**Called from:** `0x1d27b` (`ClientSpawn`, see
[`ClientSpawn.md`](ClientSpawn.md) / `../G_ACTIVE/ClientThink_real.md`'s
§1) — **the only caller**, once per spawn/respawn, passing `clientNum`.
**Args:** `(int clientNum)`

This resolves the "not attempted" item from `README.md`: "`func_0x2830`
... a loop over all entities checking `eType`/owner, freeing matching
entities via `G_FreeEntity`. Plausibly cleans up leftover hook/missile
entities owned by the respawning client." That's broadly correct.

**Correction (later pass, from
[`O3J_SelectSpawnPoint_UseClosest.md`](O3J_SelectSpawnPoint_UseClosest.md)):**
this doc originally claimed `0x2c1f0` was a genuinely new, separate
1024-slot table parallel to (but not the same memory as) `g_entities`,
based on the subtraction `0x2c1f0 - 0x1b2f0 = 0x11100` "not being a whole
multiple of `0x43c`". **That subtraction was arithmetic error** — redone
correctly, `0x2c1f0 - 0x1b2f0 = 0x10F00`, and `0x10F00 / 0x43c = 64`
*exactly*. **`0x2c1f0` is simply `&g_entities[64]`** — the 65th slot of
the same, already-known `g_entities` array, not a separate table. This is
independently confirmed by `O3J_SelectSpawnPoint_UseClosest`'s own
identical loop, which walks the same starting address and explicitly
computes `(ptr - 0x1b2f0) / 0x43c` as an entity index compared against
`num_entities` — the standard "skip all `MAX_CLIENTS` client slots, iterate
the rest of `g_entities`" idiom. The "shadow table" framing below is
retracted; the field-offset/dispatch findings themselves are unaffected
(they still describe whichever `g_entities[64..]` slot is being inspected
at each loop iteration) and are kept as originally written for history,
with this correction prepended.

---

## The loop range: `g_entities[64..1023]` (originally mis-described as "the secondary table at `0x2c1f0`")

```c
void func_0x2830( int clientNum ) {
    gentity_t *client_ent = &g_entities[clientNum];   // local14, computed but
                                                        // only used later (type==3 path)

    for ( slot = (shadow_t*)0x2c1f0;
          ((char*)slot - 0x1b2f0) / 0x43c < 0x400;      // reuses g_entities' own
                                                          // extent (1024 * sizeof(gentity_t))
                                                          // purely as a loop-count cap
          slot = (shadow_t*)((char*)slot + 0x43c) ) {    // same stride as gentity_t (0x43c)
        ...
    }
}
```

**Retracted — see the correction at the top of this doc.** `0x2c1f0` IS
`&g_entities[64]`; the loop below is a plain walk over
`g_entities[64..1023]`, i.e. every non-client slot. The field layout read
from each slot is therefore just ordinary `gentity_t` fields (several
already independently confirmed elsewhere in this project, e.g.
`+0x20c`=`classname`), not a mystery mirrored struct.

## Per-slot logic

```c
for each slot:
    if ( slot->+0x208 != 0 )          // a "skip" flag — purpose unconfirmed
        continue;

    type = slot->+0x4;                 // small-integer field, values seen: 0, 2, 3

    if ( type == 2 ) {
        if ( slot->+0x28c == 0 ) {
            func_0x1629( slot, clientNum );   // clears bit `clientNum` in a 64-bit
                                                // bitmask split across slot+0x54/+0x58
        } else if ( (slot->+0x304 - g_entities) / sizeof(gentity_t) == clientNum ) {
            func_0x15fa( slot, clientNum );   // same bit-clear, different helper —
                                                // see "0x1629/0x15fa" below
        }
    } else if ( type == 3 ) {
        if ( slot->+0x200 == clientNum
          || (slot->+0x304 - g_entities) / sizeof(gentity_t) == clientNum ) {
            G_FreeEntity( slot );   // 0x284b7, already confirmed elsewhere in this project
        }
        // (note: the exact condition here is an OR of a direct-int compare
        // at +0x200 against clientNum, and an owner-pointer-derived index
        // compare at +0x304 — both leading to the same G_FreeEntity call;
        // not independently simplified further)
    } else {
        // type == 0 (or anything else): classname-based matching against
        // slot->+0x20c (a cached char* — same offset this project has
        // already confirmed elsewhere as gentity_t.classname)
        if ( Q_stricmp( slot->+0x20c, "trigger_multiple" ) == 0 )   // 0x5c8f = Q_stricmp-shaped,
            slot->+0x32c = 0;                                         // confirmed elsewhere this
                                                                        // session (ClientConnect.md)
        if ( Q_stricmp( slot->+0x20c, "trigger_hurt" ) == 0 )
            slot->+0x32c = 0;
        if ( Q_stricmp( slot->+0x20c, "target_delay" ) == 0
          && (slot->+0x304 - g_entities) / sizeof(gentity_t) == clientNum ) {
            slot->+0x2b4 = 0;
            slot->+0x2b0 = 0;
        }
    }
```

## `0x1629`/`0x15fa` — the per-client bitmask-clear helper pair

Both are tiny (`enter 0xc`), both do exactly the same shape of operation on
a **64-bit bitmask split across two 32-bit words**:

```c
void func_0x1629( void *obj, int bit ) {   // and func_0x15fa, identical shape
    if ( bit >= 0x20 )
        *(int*)((char*)obj + 0x58) &= ~(1 << (bit - 0x20));
    else
        *(int*)((char*)obj + 0x54) &= ~(1 << bit);
}
```

**This is the exact same `+0x54`/`+0x58` field pair already found this
session in [`../G_MISSILE/func_0x20998.md`](../G_MISSILE/func_0x20998.md)**
(there, read and bit-tested after a candidate's `->touch` call, described
as "structurally resembles a per-clientNum dedup bitmask"). This
independently confirms that interpretation: `+0x54`/`+0x58` really is a
64-bit, per-`clientNum` bitmask attached to some object, and these two
functions are its "clear my bit" accessors — called here (from
`func_0x2830`) when a client (re)spawns, and elsewhere (`0x1629` also from
`0x20f11`/`0x212a7`; `0x15fa` also from `0x21249`/`0x216c3` — none of these
4 call sites independently decoded this pass) presumably on disconnect or
entity-free paths. This does **not** resolve `func_0x20998`'s own missing
caller, but it does confirm those fields' general shape.

## What's confirmed vs. not

**Confirmed**: the loop structure, the three-way `type` dispatch, the
`G_FreeEntity` call for `type==3` matching entries, the classname-based
`+0x32c`/`+0x2b4`/`+0x2b0` clearing for `type==0` (non-matching) entries,
and the `+0x54`/`+0x58` bitmask-clear connection to `func_0x20998`.

**Not confirmed** (flagged, not guessed): what `type` values `0`/`2`/`3`
actually represent; the meaning of `+0x208` (skip flag), `+0x28c`, `+0x200`,
`+0x304` (plausibly an "owner entity pointer", by the same
`(ptr - g_entities)/sizeof(gentity_t) == clientNum` idiom used elsewhere in
this project for owner checks, but not independently confirmed as such
here), `+0x32c`, `+0x2b4`, `+0x2b0`. (The loop's *range* — `g_entities[64..1023]`
— is now confirmed, see the correction at the top of this doc; it is no
longer an open question.)

## oDFs implementation status

**Not implemented.** The overall shape (free entities owned by a
respawning client, clear their bit from some per-client bitmask on
specific trigger-classname entities) is plausible as "clean up this
client's stale hooks/missiles/timers on respawn," but porting it would
still require pinning down the `type` values' meaning and the
`+0x208`/`+0x28c`/`+0x200`/`+0x304` fields — too speculative to implement
confidently even now that the loop range itself (`g_entities[64..1023]`,
no separate table) is resolved. Flagged for a future pass.
